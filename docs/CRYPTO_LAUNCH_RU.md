# Первый production-релиз: USDT в сети TON

Проверка от 22 ноября 2026 года. Для первого запуска включаем только NOWPayments и USDT в сети TON. ЮKassa остаётся в коде для следующего этапа. Рубли скрыты в витрине, калькуляторе и покупке; сервер также отклоняет новые RUB-заказы. История старых счетов сохраняет исходную валюту.

## Экономика

Количество токенов не умножается: 1000 входных токенов остаются 1000. Наценка применяется к денежным ставкам за эти токены. При `PRICE_MARKUP=2` и `BILLING_USDT_PER_USD=1` запрос с себестоимостью 0.01 USD списывает с покупателя 0.02 USDT. Калькулятор, витрина и фактическое списание используют эту модель. Коэффициент существующего ключа фиксируется первым заказом; изменение `.env` не меняет его задним числом.

| Показатель при полном расходовании ключа | Сумма |
| --- | ---: |
| Оплата и баланс клиента | 20 USDT |
| Расход поставщика при точных тарифах | 10 USD |
| Валовая прибыль при условном курсе 1 USDT = 1 USD | 10 USDT, или 50% выручки |
| Пример комиссии эквайринга 1% | 0.20 USDT |
| Остаток после этой комиссии | 9.80 USDT |

Последняя строка — не чистая прибыль: дополнительно вычитаются сеть/вывод, пополнение поставщика и конвертация, сервер, возвраты, поддержка и налоги. [NOWPayments](https://nowpayments.io/pricing) на дату проверки публикует сервисную комиссию 1%; фактические условия вашего аккаунта и минимальный платёж нужно проверить при подключении. Для пакета 2 USDT фиксированные расходы особенно существенны: если минимальная сумма провайдера выше, отключите Starter Key в админке.

Формула при полном использовании: `вклад в покрытие расходов = оплата − оплата / наценка − комиссия платежа − прочие переменные расходы`. При наценке 2 и комиссии 1% остаётся 49% выручки до остальных расходов. Для покрытия постоянных расходов F и прочих переменных расходов v от выручки требуется выручка больше `F / (0.5 − 0.01 − v)`; знаменатель должен быть положительным.

Если начислять клиенту все 20 USDT и списывать запросы по себестоимости ×1, провайдер в итоге потребует примерно 20 USD. Валовая прибыль станет нулевой, а комиссии приведут к убытку. Увеличение цены пакета само по себе этого не исправляет.

`USERS_PER_UPSTREAM_KEY=2` ограничивает места, а не делит цену токенов пополам. Два клиента по 20 USDT дают 40 USDT выручки и примерно 20 USD общего расхода при ×2. Ресурс поставщика расходуется суммарно; дополнительного множителя прибыли здесь нет.

Опубликованные [тарифы CE](https://docs.codex-everywhere.com/models/) подтверждают разные коэффициенты групп. Но `/v1/models` подтверждает только каталог, не фактическую себестоимость. Перед продажами сравните CE Usage с нашими `usage_records.cost` на обычном и потоковом запросе, кэше и длинном контексте. Без этой сверки и ваших расходов доказана формула, а не фактическая чистая прибыль. Оборванные запросы с `USAGE_UNCONFIRMED` требуют отдельной сверки.

## Данные для запуска

Шаблон: [`deploy/production.env.example`](../deploy/production.env.example). Скопируйте его в `.env` **на production-сервере** и заполните значения. Локальный `.env` сейчас оставлен в development с тестовой оплатой USDT.

Нужны: сервер и домен, HTTPS, NOWPayments API key и IPN secret, настроенный кошелёк вывода USDT TON, рабочие платные ключи/группы провайдера, SMTP, адрес оператора и пароли PostgreSQL/администратора/Grafana. Для синхронизации CE логин и пароль хранятся отдельно в `.env.ce`, который читается worker.

```dotenv
NODE_ENV=production
PAYMENT_METHODS=nowpayments
PAYMENT_CURRENCIES=USDT
NOWPAYMENTS_PAY_CURRENCY=usdtton
ALLOW_MOCK_PAYMENTS=false
SALES_ENABLED=false
PRICE_MARKUP=2
BILLING_USDT_PER_USD=1
USERS_PER_UPSTREAM_KEY=2
```

Не включайте `mock`, sandbox URL или ЮKassa в production. Тестовые пользовательские ключи, включая ключи тестового магазина ЮKassa, заблокированы в production, даже если доступны настоящие каналы. Используйте отдельную production-базу либо заранее проверьте перенос существующих данных.

**При переносе базы сохраните `KEY_ENCRYPTION_SECRET`:** его замена сделает существующие зашифрованные ключи нечитаемыми. Новый секрет создаётся только для новой базы. Смена `ADMIN_PASSWORD` в `.env` не меняет пароль уже существующего пользователя; preflight отдельно обнаруживает старый пароль разработки в базе. Для нового сервера bootstrap создаст администратора с указанным новым паролем.

## Проверка и включение

1. Сделайте резервную копию БД (`pg_dump -Fc`) и секретов в защищённое хранилище. Проверьте восстановление в отдельную БД, не в рабочую.
2. Настройте TLS на внешнем reverse proxy. В шаблоне внутренний Nginx слушает только `127.0.0.1:8080`. БД и Prometheus также не должны быть доступны из интернета. Проверьте передачу реального клиентского IP через выбранный TLS proxy: иначе все клиенты попадут в один IP-лимит. Домен/схема развёртывания ещё не заданы, TLS-конфигурация в этой проверке не разворачивалась.
3. На production-сервере соберите и запустите `docker-compose up -d --build`. Миграции применяет сервис `migrate`. Проверьте `docker-compose ps`, `/health/ready` и `/health/serving` через публичный HTTPS-адрес.
4. Добавьте или синхронизируйте платные ключи провайдера. Проверьте модели и тарифы в админке. Убедитесь, что хватает бюджета для уже проданных остатков, а не только свободных мест.
5. Выполните проверку конфигурации и базы:

   ```bash
   docker-compose run --rm --no-deps api node apps/api/dist/ops/production-check.js
   ```

   Команда только читает данные, не создаёт платежей и не тратит токены. `FAIL` и код выхода 1 означают незакрытый пункт. Успех не заменяет реальные платежи, SMTP, DNS/TLS и проверку восстановления backup. На хосте с установленными зависимостями аналогичная команда: `npm run production:check` (экспортируйте нужное окружение).
6. На отдельном staging проверьте создание реального криптосчёта и доставку подписанного IPN на `https://<домен>/api/webhooks/nowpayments`. API передаёт этот URL при создании платежа. Проверьте USDT TON, сумму, memo при его наличии, полный платёж, недоплату, повтор уведомления, опоздавший платёж и пополнение. Зачисление происходит только после `finished` с валидной подписью и полной суммой правильной монеты. Проверьте, сколько реально пришло после комиссий. Для проверки покупки переключатель продаж включается на контролируемом стенде.
7. Проверьте письма, Grafana, Prometheus и доставку аварийных оповещений. Prometheus хранит правила, но отдельного Alertmanager/внешнего канала дежурных уведомлений в Compose пока нет. Письма о низком балансе поставщика отправляет worker через SMTP.
8. После успешных проверок включите `SALES_ENABLED=true` и пересоздайте API/worker: `docker-compose up -d --no-deps --force-recreate api worker`. Проведите один контролируемый боевой платёж и запрос, затем сверку ledger и кабинетов.

Для остановки новых продаж: `SALES_ENABLED=false` и пересоздание API/worker. Оплаченные заказы и действующие платные ключи продолжат обслуживаться.

## Что пока требует оператора

Автоматических возвратов и сверки потерянного ответа создания NOWPayments-счёта нет. Если процессор создал счёт, а наш сервер не сохранил его ID, нужно сверить заказ с кабинетом до ручных действий. При переплате начисляется только купленный пакет; возврат излишка решается отдельно. При недоплате даже статус `finished` не зачисляет баланс; оператор сверяет платёж. Порядок поддержки и возвратов нужно определить до публичных продаж.

Включение live-платежей, смена рабочих секретов, реальные оплаты и запросы к платным моделям в ходе этой проверки не выполнялись: соответствующие данные вы предоставите позднее.
