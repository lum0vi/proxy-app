# Первый production-релиз: прямые USDT-переводы в TON

Актуализировано 26 ноября 2026 года. Основной способ — перевод на ваш кошелёк с проверкой через TON Center API v3. NOWPayments сохранён как альтернативный процессор, ЮKassa — для следующего этапа. При `PAYMENT_CURRENCIES=USDT` рублёвая оплата скрыта и сервер отклоняет новые RUB-заказы; рублёвый эквивалент цен остаётся виден.

## Подготовленная локальная конфигурация — 26 ноября

В корневой `.env` перенесены `TON_RECEIVER_ADDRESS` и `TONCENTER_API_KEY`. Установлены mainnet API v3, `PAYMENT_METHODS=ton`, `PAYMENT_CURRENCIES=USDT`, `TON_AUTO_APPROVE=true`, срок счёта 60 минут, `ALLOW_MOCK_PAYMENTS=false` и `SALES_ENABLED=false`. `ADMIN_ALERT_EMAIL` заполнен указанным email администратора. Реквизиты удалены из production-шаблона; рабочие `.env` и `.env.ce` исключены из отслеживания Git, локальные файлы сохранены. Это не удаляет их содержимое из старых коммитов; если они передавались в репозиторий, секреты из этих версий требуют ротации перед production.

Проверено: Compose передаёт одинаковые платёжные настройки API и worker. Один запрос Postman к `GET https://toncenter.com/api/v3/actions` с настроенным ключом и адресом завершился HTTP 200: прошли 3 проверки (HTTP-статус, JSON, массив `actions`), exit code 0. Отправка отчётов Postman в облако отключена, временный файл с реквизитами удалён. Проверка подтверждает доступ к индексатору, но не подтверждает владение кошельком, приём/вывод USDT или полный платёжный цикл.

Осталось заполнить или подготовить:

- `PUBLIC_APP_URL` — реальный HTTPS-домен приложения с настроенными DNS и TLS. Текущий HTTP-адрес отклоняется проверкой production-конфигурации.
- `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` — реквизиты почтового сервиса и подтверждённый отправитель. `SMTP_PORT` и `SMTP_SECURE` сверить с выбранным сервисом; сейчас указаны 587 и false.
- Согласованно заменить пароль существующего PostgreSQL и значения `POSTGRES_PASSWORD` / `DATABASE_URL`. Изменение переменных само по себе не меняет пароль роли в существующем томе БД.
- Заменить стартовый `KEY_ENCRYPTION_SECRET` с перешифрованием сохранённых данных и резервной копией. Случайная замена только в `.env` сделает старые ключи нечитаемыми.
- Применить новый пароль существующему администратору в БД: `ADMIN_PASSWORD` в `.env` уже отличается от стартового, но текущая учётная запись всё ещё проходит проверку со стартовым паролем.
- Подключить проверенный оплаченный ключ поставщика и провести контрольную покупку на закрытом стенде перед публичными продажами.

После исправления запуска 26 ноября контейнеры пересозданы командой `npm start` с явным `docker-compose.local.yml`. Приложение работает на `http://localhost:8080` в development; новые TON-реквизиты применены, продажи и mock-оплата выключены. Миграции завершились успешно. Корневой production `.env` и существующая база сохранены. Запуск основного Compose без локального профиля по-прежнему требует HTTPS и исправления оставшихся стартовых секретов. Для production выполнить шаги ниже и `production:check`.

## Что осталось сделать на текущем стенде

Проверка `production:check` до исправления запуска 26.11.2026 выявила отсутствие публичного HTTPS и SMTP, стартовый пароль существующего администратора и отсутствие проверенной платной ёмкости поставщика. Исправление локального запуска эти требования не закрывает. Текущий локальный стек использует TON, `SALES_ENABLED=false` и `ALLOW_MOCK_PAYMENTS=false`; опубликованные товары ещё не означают готовность принимать деньги.

1. **Подготовить кошелёк USDT TON mainnet.** Нужен публичный адрес вашего собственного кошелька. Принимать требуется USDT в TON, а не Toncoin и не USDT в другой сети. Seed-фраза и приватный ключ остаются у владельца.
2. **Получить ключ [TON Center](https://toncenter.com/)** для чтения mainnet API v3. В `.env` заполнить `TON_RECEIVER_ADDRESS` и `TONCENTER_API_KEY`. Для прямых переводов аккаунт NOWPayments, его IPN-secret и webhook не нужны. Даже в ручном режиме приложение проверяет транзакцию через индексатор.
3. **Подключить оплаченный рабочий канал моделей.** Добавить ключ поставщика, проверить каталог, закупочные тарифы и остаток. Одного пополненного аккаунта без пригодного ключа в нашем пуле недостаточно. `/health/serving` должен вернуть 200; иначе покупатель оплатит доступ, которым нельзя воспользоваться.
4. **Подготовить production-окружение.** Домен с HTTPS, постоянный сервер, PostgreSQL с резервной копией, SMTP, боевые секреты и новый пароль существующего администратора. Изменение `ADMIN_PASSWORD` в `.env` не меняет пароль уже созданного пользователя. Смена пароля через профиль сейчас не реализована; существующую учётную запись нужно отдельно обновить операционно. Текущий стартовый `KEY_ENCRYPTION_SECRET` запрещён в production: сначала нужна контролируемая ротация с перешифрованием сохранённых секретов и проверкой восстановления из резервной копии. Просто заменить его в `.env` нельзя — старые ключи станут нечитаемыми. При дальнейшем переносе базы сохраняйте уже настроенный безопасный ключ шифрования.
5. **Включить прямой TON вместо mock** по конфигурации ниже. Пересоздать API и worker; убедиться в «Админка → Заказы → Поступления USDT», что сканер работает без ошибок. Для старых счетов с комментарием при `TON_AUTO_APPROVE=true` точные подтверждённые платежи зачисляются автоматически; при `false` ждут решения администратора.
6. **Провести контролируемый платёж перед публичными продажами.** На закрытом стенде включить продажи, создать счёт на 1 USDT, отправить указанную в счёте точную сумму, оплатить комиссию сети отдельно и отправить TXID через страницу заказа. Проверить поступление на кошелёк, выдачу ключа, один реальный API-запрос и пополнение того же ключа. Убедиться, что повторная проверка транзакции не зачисляет деньги повторно. Затем завершить `production:check` и открыть production-продажи.

```dotenv
NODE_ENV=production
PUBLIC_APP_URL=https://ваш-домен
PAYMENT_METHODS=ton
PAYMENT_CURRENCIES=USDT
ALLOW_MOCK_PAYMENTS=false
TON_RECEIVER_ADDRESS=ваш_публичный_адрес_TON_mainnet
TONCENTER_API_KEY=ваш_ключ_TON_Center
TONCENTER_API_URL=https://toncenter.com/api/v3
TON_AUTO_APPROVE=true
SALES_ENABLED=false
```

Это платёжная часть конфигурации, а не полный production `.env`. Остальные обязательные поля — в `deploy/production.env.example`. Секреты не присылайте в Telegram и не публикуйте в Git. Контакт для покупателей: [@zybato](https://t.me/zybato); для разбора оплаты достаточно номера заказа, затем при необходимости ссылки на транзакцию. Сам по себе публичный хеш не подтверждает право клиента на перевод.

## Экономика и границы расчёта

1000 токенов остаются 1000: наценка применяется к денежным ставкам. При `PRICE_MARKUP=2` и `BILLING_USDT_PER_USD=1` запрос с себестоимостью 0.01 USD списывает 0.02 USDT. Калькулятор и фактический учёт используют одну модель. Покупатель платит 20 USDT и видит весь баланс 20 USDT. Если он потратит его полностью при точных тарифах, поставщику уйдёт около 10 USD: валовая прибыль — 10 USDT, маржа — 50% при условном курсе 1:1.

Это **не гарантия чистой прибыли**. Вычтите расходы на пополнение поставщика/конвертацию, сеть при возвратах и выводе, сервер, поддержку, налоги и непризнанный расход. У прямого перевода нет комиссии платёжного процессора в нашем коде; комиссии кошелька, сети и условия получения/пополнения провайдера нужно измерить на реальной операции. Для постоянных расходов F и доли переменных расходов v точка безубыточности по выручке — `F / (0.5 − v)`, если знаменатель положителен.

Если начислять все 20 USDT и списывать запросы по себестоимости ×1, валовая прибыль становится нулевой, а расходы дают убыток. Поэтому денежная наценка сохранена. Коэффициент существующего ключа фиксируется первым заказом; изменение `.env` не переписывает его задним числом. Два клиента на ключе поставщика используют его ёмкость, но не удваивают маржу.

Админка разделяет полученные оплаты и валовую прибыль по фактическому расходу. Тестовые покупки и тестовый расход исключены. Предоплата ещё не является прибылью: клиент имеет право потратить остаток. Текущий пересчёт USD → USDT использует `BILLING_USDT_PER_USD`; это управленческая оценка, не бухгалтерский расчёт по историческим курсам. До запуска сверяйте конкретные модели и их usage со списаниями в кабинете поставщика, включая кэш, длинный контекст, изображения и пиковые коэффициенты.

## Настройка и запуск

1. Подготовьте Linux-сервер с Docker Compose, публичным доменом и HTTPS reverse proxy. Пример секретов и параметров — `deploy/production.env.example`; точное место заполнения кошелька/API — раздел «Оплата прямым переводом» в корневом README. Не копируйте `.env` поверх существующего без сохранения ключа шифрования и паролей БД. `APP_BIND_ADDRESS=127.0.0.1` подходит для TLS-прокси на том же хосте.
2. Заполните `TON_RECEIVER_ADDRESS` адресом вашего mainnet-кошелька для USDT. Используйте собственный кошелёк, а не биржевой общий депозит с чужим memo. Заполните read-only `TONCENTER_API_KEY` и включите `PAYMENT_METHODS=ton`, `TON_AUTO_APPROVE=true`, `ALLOW_MOCK_PAYMENTS=false`, `PAYMENT_CURRENCIES=USDT`. Seed-фразу и signing key серверу не передавайте. NOWPayments API/IPN секреты для этого варианта не нужны.
3. Оставьте `SALES_ENABLED=false`, настройте SMTP, случайные session/Grafana/DB секреты. Для новой базы создайте новый ключ шифрования; при переносе базы сохраните существующий. У существующего администратора отдельно замените стартовый пароль: изменение `ADMIN_PASSWORD` не меняет уже сохранённый хеш, а формы смены пароля в профиле пока нет. Тестовые ключи не работают в production; не выдавайте их покупателям.
4. Создайте резервную копию PostgreSQL и сохраните ключ шифрования отдельно. Проверьте восстановление. Соберите сервисы, выполните миграции и запустите API/worker/Nginx:

   ```bash
   docker-compose build api worker migrate nginx
   docker-compose run --rm migrate
   docker-compose up -d
   docker-compose run --rm --no-deps api node apps/api/dist/ops/production-check.js
   ```

   Миграция `013_ton_direct_payments.sql` добавляет журнал переводов и состояние сканирования, не меняя баланс существующих ключей. Для обновления уже работающих контейнеров после изменения `.env` используйте `docker-compose up -d --no-deps --force-recreate api worker nginx`.
5. Добавьте реальные ключи поставщика, проверьте каталог/тарифы и запас бюджета под уже проданные остатки. `/health/ready` подтверждает БД; `/health/serving` должен вернуть 200, когда есть работающий upstream. Эти проверки не заменяют проверку платежей.
6. На закрытом staging включите продажи и выполните небольшой реальный USDT-перевод с проверкой TXID, выдачу ключа и пополнение. Убедитесь в поступлении на ваш кошелёк, правильной сумме ledger, отсутствии повторного зачисления и реальном расходе поставщика. Для старых счетов ручной режим проверяется через `TON_AUTO_APPROVE=false` и перезапуск API/worker. Возвраты, переплату и комиссии сверьте отдельно. Реальный перевод в ходе разработки не выполнялся.
7. Откройте «Админка → Заказы»: сканер должен быть свежим, без ошибок. Prometheus: `proxiapp_ton_scan_lag_seconds`, `proxiapp_ton_scan_errors`, `proxiapp_ton_payments_review`. Grafana содержит панели задержки и ручной очереди, Prometheus — правила `TonPaymentScannerStale`/`TonPaymentsNeedReview`. После обновления файлов мониторинга пересоздайте контейнеры: `docker-compose up -d --no-deps --force-recreate prometheus grafana` (это также обновляет файловые bind mounts Colima). Доставка этих alerts требует внешнего Alertmanager/канала — в Compose он пока не настроен. Проверьте SMTP и уведомления о балансе поставщика.
8. Закройте все `FAIL` в `production:check`, проверьте публичный TLS, backup restore, email и доступность upstream. Затем включите продажи в production и проведите контролируемую сверку первого платежа и запроса.

Остановка новых продаж: `SALES_ENABLED=false` + пересоздание API/worker. Действующие ключи и обработка уже принятых оплат продолжают работать.

## Правила зачисления и ручной работы

Автоматически принимается только успешное действие `jetton_transfer` с `finality="finalized"` (также допускается документированное enum-значение `2`) и `trace_mc_seqno_end > 0` из TON Center mainnet. Проверяются адрес получателя, контракт USDT `EQCxE6mUtQJKFnGfaROTKOt1lZbDiiX1kCixRv7Nw2Id_sDs`, сумма в целых миллионных долях и совпадение TXID с транзакцией подтверждённого действия. Время перевода должно попадать между созданием и окончанием счёта. Поздняя индексация своевременного платежа допустима. Один action может быть зачислен только один раз; одобрение, статус оплаты и audit log сохраняются транзакционно в PostgreSQL. Выдача ключа повторяется worker, если в момент оплаты нет свободной ёмкости.

Для новых счетов требуется точное совпадение суммы и проверка TXID. Следующие правила ручного разбора относятся к ранее выданным счетам с комментарием.

Переплата, недоплата, поздний перевод, пропущенный комментарий и ручной режим попадают в очередь. Автоматическое объединение частичных переводов не реализовано; недоплату нельзя одобрить. Администратор сверяет принадлежность перевода клиенту, вводит основание и одобряет подходящую полную оплату. При переплате зачисляется сумма счёта; излишек возвращается отдельно. Отклонение не выполняет перевод назад. Ошибочное отклонение можно исправить новым одобрением с записью в журнале, но уже использованный перевод повторно зачислить нельзя.

Хеш от покупателя не доказывает владение переводом: транзакции публичны. Для платежа без комментария сверяйте отправляющий кошелёк с клиентом по независимому подтверждению владения. Не присваивайте неизвестные поступления на основании публичной ссылки или картинки. Ключи от кошелька и seed-фразы не запрашивайте.

Worker опрашивает блокчейн примерно раз в минуту (при долгих задачах провайдера цикл может увеличиваться). Читает фиксированное временное окно с запасом по времени и сохраняет курсор/страницу после обработки. При сбое не двигает курсор, после перезапуска продолжает с него. Смена кошелька не исключает адреса старых счетов. При большом потоке проверьте скорость разгребания страниц и лимиты вашего API-тарифа; оповещение о задержке обязательно. Администратор может адресно проверить пропущенный перевод по хешу.

## На чём основана интеграция и что проверено локально

Контракт сверялся с публичной [OpenAPI TON Center](https://toncenter.com/api/v3/doc.json), [описанием actions](https://docs.ton.org/api/v3/actions-and-traces/get-actions) и [правилами USDT/jetton-платежей TON](https://docs.ton.org/applications/payments/jettons). Сервис доверяет HTTPS-ответам индексатора; собственная TON-нода и проверка криптографических proofs не реализованы. Индексатор обеспечивает распознавание цепочки перевода и подлинного контракта; в коде повторно проверяются его итоговые поля. Read-only запрос к реальному публичному API 25 ноября показал `finality="finalized"`, хотя OpenAPI описывает число `2`; поддержаны оба варианта, а pending/confirmed отклоняются. Полный цикл с вашим кошельком и полнота индексации всё равно требуют контрольного реального платежа перед запуском.

`apps/api/src/services/ton-payments.integration.test.ts` запускает приложение, PostgreSQL и локальный HTTP-имитатор TON Center. Исходящая сеть перехватывается; неожиданные внешние вызовы отклоняются. Проверяются успешная оплата и пополнение, повтор/конкурентная обработка, фальшивый токен, чужой адрес, неуспешная/незавершённая транзакция, комментарий, недоплата/переплата, сроки, ручные решения/права, заявки клиентов, outage и сохранённая пагинация. Это проверка нашего кода против формы официального API, а не доказательство живой оплаты.

## Альтернатива NOWPayments

При `PAYMENT_METHODS=nowpayments` нужны API key/IPN secret и HTTPS callback `/api/webhooks/nowpayments`. Зачисление — только по `finished` с валидной HMAC-подписью и правильной полной суммой. Потерянный ответ создания такого счёта и возвраты требуют сверки с кабинетом; автоматического восстановления отсутствующего ID нет. Этот путь не используется для прямого TON-перевода.
