# Как пользоваться Ksapi

Эта инструкция ведёт от пустой машины до первой продажи и первого запроса через купленный ключ.

## 1. Что нужно заранее

- macOS с Colima или Linux с Docker Engine;
- Docker Compose (`docker-compose`) либо новый синтаксис `docker compose`;
- Node.js 24.22.3+ для локальных проверок; в Docker используется Node.js 24 LTS;
- CE-аккаунт с положительным PayGo-балансом и ключом нужной группы для платных запросов;
- для production: домен, HTTPS, ЮKassa и/или NOWPayments, SMTP.

Для PayGo-группы вы пополняете баланс CE. Ключи можно добавлять через админку или выпускать автоматически с уже пополненного аккаунта. Ksapi выдаёт покупателям собственные ключи и учитывает расход. Отдельная группа Free Trial предназначена для тестов.

## 2. Подготовьте `.env`

Этот шаг нужен для новой установки. Если `.env` и база уже существуют, сохраните текущие реквизиты и переходите к запуску: не копируйте шаблон поверх рабочего файла и не генерируйте новый ключ шифрования.

```bash
cp .env.example .env
openssl rand -hex 32
openssl rand -hex 32
```

Первый результат вставьте в `SESSION_SECRET`, второй — в `KEY_ENCRYPTION_SECRET`. Также обязательно поменяйте:

```dotenv
NODE_ENV=development
PUBLIC_APP_URL=http://localhost:8080
ADMIN_EMAIL=you@example.com
ADMIN_PASSWORD=длинный-уникальный-пароль
POSTGRES_PASSWORD=другой-длинный-пароль
DATABASE_URL=postgres://proxiapp:тот-же-пароль@postgres:5432/proxiapp
GRAFANA_ADMIN_PASSWORD=ещё-один-пароль

PRICE_MARKUP=2
USERS_PER_UPSTREAM_KEY=2
PAYMENT_METHODS=mock
ALLOW_MOCK_PAYMENTS=true
```

`PRICE_MARKUP` и `USERS_PER_UPSTREAM_KEY` — разные параметры:

- `PRICE_MARKUP=2` задаёт множитель цены пакета и ставок запроса. Покупка пакета 20 USDT начисляет 20 USDT на баланс ключа;
- `USERS_PER_UPSTREAM_KEY=2` разрешает закрепить за одним CE API key максимум два проданных ключа.

Не меняйте `KEY_ENCRYPTION_SECRET` после добавления upstream-ключей без отдельной процедуры re-encryption: старые ciphertext станут нечитаемыми. Смена `SESSION_SECRET` безопасна, но завершит все активные сессии.

## 3. Запустите стек через Colima

```bash
colima start --cpu 4 --memory 8 --disk 60
npm start
docker-compose ps
curl -fsS http://localhost:8080/health/live
curl -fsS http://localhost:8080/health/ready
```

`npm start` использует основной Compose и `docker-compose.local.yml`: поднимает полный стек на localhost, выключает продажи и mock-оплату, сохраняя `.env` и данные. Требуемая версия Node.js работает внутри Docker; для самой команды достаточно установленного на хосте Node.js 20+. Остановка — `npm stop`, диагностика — `npm run local:logs`.

При первом старте `migrate` применит SQL-миграции, `seed` создаст каналы CE, пакеты, ставки моделей и первого администратора. Данные сохраняются в томах Docker. Если в старом `.env` вручную задан `PROXY_ALLOWED_PATHS`, добавьте пути Messages и Gemini из [.env.example](../.env.example).

После обновления кода повторите `npm start`. Эквивалент без npm: `docker-compose -f docker-compose.yml -f docker-compose.local.yml up -d --build --wait`. Обычный `docker-compose up -d --build` и следующие команды этой инструкции используют `.env` без локальных переопределений: при `NODE_ENV=production` обязательны HTTPS и production-секреты. `restart` не пересобирает код и не перечитывает окружение.

Если сервис `migrate` завершился с кодом 1, причину можно прочитать командой `docker-compose logs --no-color --tail=100 migrate`. После успешного запуска его состояние `Exited (0)` нормально: миграции выполняются один раз, затем работают API и worker.

Адреса:

- приложение: `http://localhost:8080`;
- readiness: `http://localhost:8080/health/ready`;
- наличие проверенного канала для запросов: `http://localhost:8080/health/serving` (`503` на пустом стенде);
- Grafana: `http://localhost:8080/grafana/`;
- Prometheus: `http://127.0.0.1:9090`;
- OpenAPI: `http://localhost:8080/openapi.yaml`.

Если у вас установлен только новый Compose, заменяйте `docker-compose` на `docker compose` во всех командах.

### Доступ с другого компьютера в локальной сети

Узнайте Wi-Fi IP Mac с приложением (`ipconfig getifaddr en0`). Например, для адреса `172.20.10.4` задайте в `.env`:

```dotenv
NODE_ENV=development
APP_BIND_ADDRESS=0.0.0.0
APP_PORT=8080
PUBLIC_APP_URL=http://172.20.10.4:8080
ADDITIONAL_BROWSER_ORIGINS=http://localhost:8080,http://127.0.0.1:8080
```

Примените `docker-compose up -d --build`. Для этого режима используется основной Compose: `npm start` ограничивает доступ одним Mac через localhost. На втором компьютере откройте `PUBLIC_APP_URL`; на первом также разрешены перечисленные локальные адреса. Если macOS блокирует доступ, разрешите входящие подключения для процесса, публикующего порт Colima, в брандмауэре. При смене IP обновите `PUBLIC_APP_URL`.

`Request origin is not allowed` означает, что адрес открытой вкладки не входит в разрешённый список. Такая проверка выполняется до проверки пароля, например при показе ключа. Список используется и для CORS, и для защиты запросов с cookie. Указывайте только доверенные адреса самого приложения вместе со схемой и портом; пути, маски и произвольные сайты запрещены. В production дополнительные адреса должны использовать HTTPS. Для отдельного Vite dev-сервера можно явно добавить `http://localhost:5173`. Входить в аккаунт на разных адресах нужно отдельно, поскольку cookie привязаны к хосту.

## 4. Подключите Codex Everywhere

При `CE_AUTO_PROVISION_KEYS=false` добавляйте ключи вручную. Это режим по умолчанию.

1. В кабинете CE получите рабочий ключ для каждой нужной группы. В Ksapi войдите с данными администратора и откройте **Админка → Провайдеры → Добавить upstream-ключ**.
2. Выберите пул `Codex Everywhere` для **Plus PayGo**. Для остальных групп выберите готовый канал: `CE · Codex Pro PayGo`, `CE · Claude Max PayGo`, `CE · Claude Kiro PayGo`, `CE · Grok Heavy PayGo`, `CE · DeepSeek Official`, `CE · GPT Image PayGo` или `CE · Gemini Antigravity`. Для Gemini нужен ключ с доступом к этой группе; он может отсутствовать в списке выдачи CE. CE ограничивает Claude Max клиентом Claude Code.
3. Укажите метку, секрет и реальный предел параллельных запросов. Для Free Trial поставьте «Только для тестовой оплаты»: такой ключ работает только с mock-заказами, когда `PAYMENT_METHODS=mock`, `ALLOW_MOCK_PAYMENTS=true` и среда не production. Не добавляйте один секрет в несколько каналов. Покупателю достаточно одного ключа Ksapi для доступных моделей всех связанных каналов.
4. Проверьте статус в **Ключи провайдера**. Ksapi проверяет каталог при добавлении и периодически обновляет его. Ставка должна быть задана и модель должна быть в проверенном каталоге. Новые модели без ставки появятся на витрине с отметкой «Ставка не задана»; укажите цену в **Тарифы моделей**, когда подтвердите себестоимость. Для `codex-auto-review` отдельная ставка CE в публичных таблицах не указана.
5. Сверьте **Тарифы моделей** с [актуальными ставками CE](https://docs.codex-everywhere.com/models/). Проверьте тестовый запрос через каждый включённый канал и сравните расход с кабинетом CE перед началом продаж. Для GPT задан консервативный множитель `2` после `272000` входных токенов.

Секрет CE после сохранения нельзя получить через admin API: интерфейс показывает только hint. Он расшифровывается внутри proxy непосредственно перед upstream-запросом и не пишется в логи.

### Автоматический выпуск ключей CE

1. Создайте файл `.env.ce` рядом с `docker-compose.yml`. Этот файл читает только контейнер worker. Укажите почту и пароль аккаунта CE собственными значениями. Worker откроет свою сессию и зашифрует её токены перед сохранением в PostgreSQL.

   ```dotenv
   CE_PROVISION_EMAIL=you@example.com
   CE_PROVISION_PASSWORD='your CE password'
   ```
2. Соберите приложение, запустите миграции и посмотрите группы аккаунта. Команда выведет их ID, названия и текущий баланс CE.

   ```bash
   docker-compose up -d --build
   docker-compose exec worker node apps/api/dist/worker.js --ce-groups
   ```

3. В основном `.env` задайте флаг и пары `slug пула:ID группы`. Возьмите ID из вывода предыдущей команды. Например, если ID **Codex Plus Pool (PayGo)** равен `17`, а **Codex Pro Pool (PayGo)** — `23`:

   ```dotenv
   CE_AUTO_PROVISION_KEYS=true
   CE_PROVISION_GROUPS=codex-everywhere:17,ce-codex-pro:23
   CE_PROVISION_FREE_SLOTS=2
   ```

4. Пересоздайте worker и проверьте новые ключи в **Админка → Провайдеры**.

   ```bash
   docker-compose up -d --no-deps --force-recreate worker
   docker-compose logs --tail=50 worker
   ```

Worker проверяет запас примерно раз в минуту, создаёт ключ для настроенной PayGo-группы при нехватке мест и открывает продажи после проверки каталога. Лимит расходов нового ключа CE равен максимальной себестоимости пакета в пуле, умноженной на число покупателей на ключ. Worker проверяет баланс CE перед выпуском. Пополнение баланса выполняется в CE отдельно. Для возврата к ручному режиму поставьте `CE_AUTO_PROVISION_KEYS=false` и пересоздайте worker.

### Если ключ провайдера исчерпан

Клиентский ключ и ключ провайдера имеют отдельные балансы. Пополнение клиентского ключа увеличивает оплаченный остаток покупателя. Оно не увеличивает лимит старого ключа CE.

При пополнении система выбирает проверенный ключ провайдера с достаточным бюджетом и свободным местом. Во время запросов замена подбирается также при исчерпании старого ключа или недостаточном остатке для конкретного запроса с учётом уже выполняющихся запросов. Число клиентов на каждом ключе по-прежнему ограничено `USERS_PER_UPSTREAM_KEY`. Сам клиентский ключ, его баланс и история сохраняются.

При `CE_AUTO_PROVISION_KEYS=true` worker поддерживает запас ключей. Почти пустые ключи, на которых недостаточно средств для самого большого пакета, не считаются полноценным запасом. Когда аккаунт CE пополнен и нужная PayGo-группа доступна, worker создаёт новый ключ с новым лимитом и проверяет каталог моделей. Увеличение лимита старого CE-ключа не выполняется.

Если замена уже готова, следующий запрос проходит через неё. Если запас закончился, запрос временно вернёт `503`, без списания с клиента за неотправленный запрос. Дождитесь выпуска ключа и повторите запрос. Уже принятый провайдером запрос автоматически не повторяется, чтобы не получить двойной расход. Подтверждённый платёж, для которого пока нет места, остаётся в статусе `PAID`; worker повторяет зачисление после появления ключа. До создания счёта отсутствие подходящей ёмкости блокирует оплату.

При `CE_AUTO_PROVISION_KEYS=false` замена среди уже добавленных ключей работает, но новый ключ нужно добавить через админку. Деньги на общем балансе CE сами по себе не создают ключ в Ksapi.

Если вход по паролю требует второго фактора, можно использовать `CE_PROVISION_REFRESH_TOKEN` вместо пары почта и пароль. Возьмите `refresh_token` из отдельной браузерной сессии CE в **DevTools → Application → Local Storage**. При истечении или отзыве этой сессии укажите новый токен и пересоздайте worker.

Выпуск использует HTTP API кабинета CE (`/api/v1/keys`), которое CE не публикует как отдельный партнёрский контракт. Параметры сверены с веб-клиентом CE, выпуск и обработку сбоев мы проверили на локальном имитаторе.

### Активные ключи CE и привязка к покупателям

В **Админка → Провайдеры → Ключи в аккаунте CE** отображаются ID, метка, группа, статус, расход, лимит и остаток ключа CE. Для подключённых ключей видны пользователи и остатки их клиентских ключей в USDT. Для ключей CE, ещё не добавленных к нам, будет указано «Не подключён к Ksapi».

В **Админка → Пользователи** нажмите на email. Карточка показывает активные ключи этого пользователя, начисления, расход, остаток USDT и привязанные ключи поставщиков — основной и дополнительные модельные каналы. Отдельно видны остаток CE, время его проверки и число клиентских ключей, которые используют тот же ключ поставщика. Остаток CE общий: его нельзя складывать по строкам клиентов как независимые деньги. Переключатель позволяет показать также неактивные и исчерпанные ключи.

Для синхронизации добавьте в `.env`:

```dotenv
CE_KEY_SYNC_ENABLED=true
CE_KEY_SYNC_INTERVAL_MS=300000
```

В `.env.ce` укажите `CE_PROVISION_EMAIL` и `CE_PROVISION_PASSWORD` либо только `CE_PROVISION_REFRESH_TOKEN`, как описано выше для автовыпуска. Эти данные доступны только worker. Перезапустите приложение командой `docker-compose up -d --build`. Миграция 011 создаст таблицы снимков. При `CE_AUTO_PROVISION_KEYS=true` синхронизация также включена автоматически. Кнопка «Синхронизировать с CE» ставит обновление в очередь worker; запуск обычно занимает до минуты.

Синхронизация читает `GET /api/v1/auth/me` и все страницы `GET /api/v1/keys?page=1&page_size=100&sort_by=created_at&sort_order=asc` с access token аккаунта. Метод получения одного ключа — `GET /api/v1/keys/{id}`. Формат сверен с [веб-клиентом CE](https://codex-everywhere.com/keys) 17 ноября 2026 года; отдельного стабильного B2B-контракта этих методов CE нам не предоставил.

Активным в снимке считается ключ со статусом `active`, не истёкшим сроком и неиспользованным индивидуальным лимитом. При положительном `quota` остаток равен `max(0, quota - quota_used)`. `quota = 0` означает отсутствие индивидуального лимита ключа, а не нулевой остаток или бесконечные средства: действуют общий счёт / подписка и ограничения группы. Фактическая доступность моделей по-прежнему проверяется отдельно через каталог.

Снимок связывается с вручную добавленными и автоматически выпущенными ключами по HMAC-отпечатку. Секреты из ответа CE не сохраняются в снимке и не возвращаются в админку. Синхронизация только читает CE: не меняет там лимиты, не включает отключённые ключи и не добавляет найденные ключи в продажу автоматически. Локальные счётчики маршрутизации тоже не перезаписываются снимком; расход CE и наш учёт показаны отдельно. Ошибка или изменение списка между страницами оставляет предыдущий снимок с отметкой об устаревании. Полный успешный список отмечает удалённые ключи как отсутствующие, сохраняя клиентские балансы и историю.

Наш API (только с сессией администратора):

- `GET /api/admin/provider-keys?activeOnly=true&page=1&pageSize=25` — снимок CE, связи и состояние синхронизации;
- `POST /api/admin/provider-keys/refresh` — запрос обновления, ответ `202`;
- `GET /api/admin/users/{id}/keys?activeOnly=true&page=1&pageSize=25` — ключи пользователя и остатки по привязкам.

Для серверного кода доступны `listProviderKeys()` и `listUserKeys()` из `services/provider-keys.ts`; `syncCeKeys()` использует API аккаунта CE. В ответе учитывайте `sync.stale` / `remoteStale`: последний сохранённый остаток не является свежим подтверждением при ошибке синхронизации.

### Что произойдёт при capacity = 2

Один подтверждённый ключ поставщика даёт до двух мест. Покупка закрепляет одно место в доступном канале. Когда покупатель впервые запрашивает модель из другого канала, Ksapi занимает там место при наличии. Если Claude-канал заполнен, третий покупатель сможет работать с другими доступными моделями, пока не появится место для Claude. Добавление ещё одного ключа этой группы даёт дополнительные места.

Неоплаченный заказ резервирует место на час для ЮKassa, до срока криптосчёта для NOWPayments и на 24 часа для локального теста. Поздний подтверждённый платёж сохраняется как `PAID`. При отсутствии свободного ключа worker повторит выдачу после появления места.

## 5. Добавьте другого провайдера или New API

В **Админка → Провайдеры → Добавить провайдера** заполните:

- название и уникальный slug;
- Base URL и протокол: Responses/Chat Completions, только Chat, Anthropic Messages, Gemini или Images;
- при необходимости — родительский пул, если нужен общий каталог и один клиентский ключ;
- **Пользователей на upstream-ключ** — например `5`.

После этого:

1. добавьте один или несколько upstream API keys;
2. добавьте ставки для каждой разрешённой модели;
3. в **Админка → Товары** создайте товар, выберите этот provider pool, wholesale-лимит, срок и concurrency;
4. сделайте тестовый заказ и запрос.

Так можно подключить CE напрямую, собственный Sub2API/New API или другой совместимый API. Каждый канал передаёт запросы в своём формате. Claude можно вызывать через `/v1/messages`, Gemini — через `/v1beta/models/{model}:generateContent` и `:streamGenerateContent?alt=sse`.

## 6. Создайте товар и проверьте цену

Преднастроены бессрочные пакеты `Starter Key`, `Developer Key` и `Extended Key`. При `PRICE_MARKUP=2` покупатель может выбрать `2 USDT`, `20 USDT` или `50 USDT`. Оплата целиком поступает на баланс ключа. Доступность моделей обновляется по результатам проверки каталогов подключённых ключей.

Чтобы пополнить бессрочный ключ, откройте **Кабинет → Расход → Пополнить ключ**, выберите пакет и оплатите его. После подтверждения сумма прибавится к остатку. Сам ключ, история и настройки клиента сохранятся.

Тарифы витрины и калькулятор показывают розничные ставки в USDT. Фактическое списание видно в истории запроса. Оплаченный баланс доступен всем моделям ключа. Чтение кэша учитывается по собственной ставке; у Claude отдельно учитывается и запись в кэш.

Изменение `PRICE_MARKUP` влияет на витрину и новые ключи после рестарта. Пополнение оплачивается по текущей цене пакета и начисляется по полной сумме платежа. Множитель списания пополненного ключа остаётся зафиксирован условиями его первоначального заказа.

Витрина показывает цену в USDT и ориентировочный эквивалент в ₽. Рублёвый платёж идёт через ЮKassa (карты / СБП), криптоплатёж — в USDT в сети TON. При создании рублёвого счёта фиксируются сумма RUB, курс и сумма USDT к зачислению; позже курс не меняет оплаченный баланс. В калькуляторе можно указать модель и объёмы входа, кэша и ответа. **Кабинет → Расход** показывает списания и статусы запросов по выбранному ключу.

## 9. Включите реальные платежи

### Учёт в USDT и курс рубля

```dotenv
DEFAULT_CURRENCY=USDT
BILLING_USDT_PER_USD=1
PRICE_RATES_URL=https://api.coingecko.com/api/v3/simple/price?ids=tether&vs_currencies=usd,rub&include_last_updated_at=true
PRICE_RATES_API_KEY=
USDT_RUB_RATE=
```

`BILLING_USDT_PER_USD` — коммерческий коэффициент перевода себестоимости поставщика из USD в USDT. Это правило ценообразования, а не утверждение о неизменном рыночном курсе. Цена нового пакета = себестоимость USD × `PRICE_MARKUP` × этот коэффициент, округлённая до двух знаков. Для уже купленного ключа коэффициент списания сохраняется: сумма USDT первого заказа / его оптовый лимит USD. Пополнение добавляет USDT и не меняет этот коэффициент.

При пустом `USDT_RUB_RATE` сервер получает USDT/RUB из CoinGecko, кеширует на 5 минут и не создаёт рублёвый счёт по котировке старше 15 минут. При сбое пользователь может повторить оплату позже или выбрать USDT. Для фиксированного курса укажите, например, `USDT_RUB_RATE=100.50` — это ваш установленный курс, его нужно обновлять самостоятельно. Курс и время котировки сохраняются в заказе. Рублёвые эквиваленты баланса и ставок справочные; списание идёт в USDT.

Миграция 010 сохраняет числовые остатки и историю списаний 1:1 в USDT. Исходные суммы и валюты старых счетов остаются для сверки и поздних уведомлений. Новые заказы хранят `amount`/`currency` для платежа и `creditAmount` в USDT для начисления. Например, при курсе 100 пакет 20 USDT стоит 2000 ₽ и начисляет 20 USDT. Миграция применяется командой `docker-compose up -d --build` через сервис `migrate`; перед обновлением сохраните резервную копию PostgreSQL.

### ЮKassa — рубли, карты и СБП

На странице **Купить ключ** или **Пополнить** выберите **₽ · Рубли**. Карточки пакетов и строка «К оплате» покажут рублёвую сумму, а отдельная строка — сколько USDT поступит на ключ. При создании счёта сервер фиксирует курс; изменение курса после этого не меняет сумму счёта. При выборе **USDT** оплата идёт в сети TON через NOWPayments.

По умолчанию `PAYMENT_CURRENCIES=USDT`: рублёвая оплата и справочные курсы скрыты. Для будущего подключения рублей добавьте `RUB` в этот параметр. В локальном режиме `PAYMENT_METHODS=mock`, `PAYMENT_CURRENCIES=USDT,RUB` доступны обе валюты для проверки покупки и пополнения. Счёт явно помечен как тестовый: кнопка подтверждения не списывает деньги. Для рублёвого теста также требуется доступный курс или явно заданный `USDT_RUB_RATE`. Без данных магазина настоящая оплата картой и СБП не работает.

```dotenv
NODE_ENV=production
PUBLIC_APP_URL=https://your-domain.example
PAYMENT_METHODS=yookassa,nowpayments
PAYMENT_CURRENCIES=USDT,RUB
ALLOW_MOCK_PAYMENTS=false
SALES_ENABLED=false
YOOKASSA_SHOP_ID=your-shop-id
YOOKASSA_SECRET_KEY=your-live-secret
YOOKASSA_TEST_MODE=false
YOOKASSA_API_URL=https://api.yookassa.ru/v3
YOOKASSA_RECEIPTS_ENABLED=false
YOOKASSA_VAT_CODE=1
```

Если пока подключаете только рубли, укажите `PAYMENT_METHODS=yookassa` и `PAYMENT_CURRENCIES=RUB`. Добавляйте `nowpayments` после заполнения его реквизитов. Секреты сохраняйте в локальном `.env`. После изменения настроек пересоздайте API и worker: `docker-compose up -d --no-deps --force-recreate api worker`.

1. Подключите магазин и включите оплату картами и СБП в ЮKassa. Оба доступных в магазине способа выбираются на платёжной странице ЮKassa. Наш сервер не принимает реквизиты карты.
2. Добавьте в кабинете ЮKassa HTTP-уведомление `payment.succeeded` на `https://your-domain.example/api/webhooks/yookassa`.
3. Если передаёте чек через ЮKassa, включите `YOOKASSA_RECEIPTS_ENABLED=true` и задайте `YOOKASSA_VAT_CODE` и при необходимости `YOOKASSA_TAX_SYSTEM_CODE` согласно настройке магазина. В чек попадут email покупателя, услуга и фактическая сумма RUB. По умолчанию чек через API отключён: настройка фискализации зависит от вашего магазина.
4. Сначала используйте тестовый магазин с `NODE_ENV=development`, `YOOKASSA_TEST_MODE=true`, `PAYMENT_METHODS=yookassa`, `ALLOW_MOCK_PAYMENTS=false`, `SALES_ENABLED=true` и публичным HTTPS-адресом staging. Проверьте покупку и пополнение. Тестовый счёт помечается в заказе; не используйте его для выдачи реального оплаченного доступа клиентам.
5. Переключите ключи магазина на боевые, установите `YOOKASSA_TEST_MODE=false`, проверьте доставку уведомлений и затем включите `SALES_ENABLED=true`.

Каждый POST `/v3/payments` использует ID заказа как ключ идемпотентности. Уведомление служит сигналом: сервер сам запрашивает платёж у ЮKassa с авторизацией и сверяет магазин, режим test/live, статус `succeeded`, `paid`, ID, метаданные, валюту и сумму. Поля `paid` и `amount` из входящего webhook не используются. Зачисление выполняется один раз, даже при повторах или поздней доставке.

Если ЮKassa создала платёж, но ответ о создании потерялся и ID платежа не сохранился у нас, подтверждённое уведомление `payment.succeeded` восстанавливает связь с заказом. Перед этим сервер проверяет все условия через авторизованный GET. Заказ получает оплаченную сумму один раз; если места у провайдера пока нет, выдачу повторит worker. Это восстановление работает для ЮKassa; для потерянных криптосчетов требуется ручная сверка.

Контракт интеграции: [создание платежа](https://yookassa.ru/developers/payment-acceptance/getting-started/quick-start), [HTTP-уведомления](https://yookassa.ru/developers/using-api/webhooks).

### NOWPayments — USDT в сети TON

```dotenv
PAYMENT_METHODS=yookassa,nowpayments
PAYMENT_CURRENCIES=USDT,RUB
NOWPAYMENTS_API_KEY=...
NOWPAYMENTS_IPN_SECRET=...
NOWPAYMENTS_PAY_CURRENCY=usdtton
NOWPAYMENTS_API_URL=https://api.nowpayments.io/v1
```

Настройте в NOWPayments кошелёк выплат USDT и IPN secret. Callback передаётся автоматически: `https://your-domain.example/api/webhooks/nowpayments`. В API указывается точная `pay_amount` в USDT и монета `usdtton`; техническая оценка `price_amount`/`price_currency=usd` хранится отдельно для сверки IPN. Покупатель видит USDT и сеть TON, адрес, memo (если требуется) и срок счёта. Не отправляйте нативный Toncoin вместо USDT. Сетевая комиссия оплачивается кошельком отдельно от суммы счёта.

Подтверждение требует `finished`, корректной HMAC-подписи, совпадения ID и исходной оценки, а также полной фактической оплаты в USDT TON. Счёт с другой монетой или суммой отклоняется ещё при создании. Недоплата не начисляет баланс; комиссия платёжного сервиса не уменьшает сумму зачисления USDT. Проверьте доступность USDT TON и минимальную сумму для вашего кошелька выплат в [NOWPayments](https://nowpayments.io/help/payments/common/what-is-the-minimum-payment-amount): слишком маленький пакет может быть отклонён. [Документация API](https://documenter.getpostman.com/view/7907941/S1a32n38).

Старые Stripe- и Toncoin-счета сохраняют исходные условия; для поздних Stripe-уведомлений оставьте `STRIPE_SECRET_KEY` и `STRIPE_WEBHOOK_SECRET`. Создание новых Stripe-счетов отключено.

Поля кошелька в профиле — только контактный публичный адрес пользователя. Приложение не хранит private key/seed и не является custodial wallet.

## 10. Email-уведомления

Заполните SMTP-параметры. Worker раз в минуту ставит и отправляет дедуплицированные уведомления:

- ключ создан;
- до истечения осталось 7/3/1 дней;
- осталось 20/10/5 процентов лимита.

Без SMTP письмо остаётся в очереди с причиной `SMTP_NOT_CONFIGURED`. Ошибка доставки также оставляет его для повтора с задержкой от минуты до часа. После настройки SMTP worker продолжит отправку; несколько worker не обрабатывают одно письмо одновременно. После сбоя процесса между приёмом письма SMTP-сервером и записью результата повторная доставка всё же возможна. Старые записи `SENT`, созданные до этого исправления при отключённом SMTP, автоматически не переотправляются.

### Низкий баланс аккаунта провайдера

Для CE есть отдельная проверка **общего баланса аккаунта**, полученного через API кабинета. Проверка работает независимо от наличия свободных ключей. В автоматическом режиме она включена всегда. Для мониторинга при ручном добавлении ключей задайте `CE_BALANCE_MONITOR_ENABLED=true`.

В `.env` задайте параметры:

```dotenv
CE_BALANCE_MONITOR_ENABLED=true
PROVIDER_BALANCE_LOW_USD=20
PROVIDER_BALANCE_CHECK_INTERVAL_MS=300000
PROVIDER_BALANCE_ALERT_REPEAT_HOURS=24
ADMIN_ALERT_EMAIL=you@example.com
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=your-smtp-user
SMTP_PASSWORD=your-smtp-password
SMTP_FROM=Ksapi <notifications@your-domain.example>
```

В `.env.ce` укажите `CE_PROVISION_EMAIL` и `CE_PROVISION_PASSWORD` либо `CE_PROVISION_REFRESH_TOKEN`, как в разделе автоматического выпуска. Этот файл читает только worker. Для проверки баланса не требуется включать выпуск ключей или заполнять `CE_PROVISION_GROUPS`.

После изменения конфигурации выполните `docker-compose up -d --build`. В **Админка → Обзор** и **Провайдеры** появятся остаток, время проверки и состояние уведомления. Если остаток не превышает `$20`, письмо уходит на `ADMIN_ALERT_EMAIL`. Пока баланс остаётся низким, повтор отправляется не чаще раза в сутки. После пополнения выше порога и нового снижения уведомление срабатывает снова.

При отсутствии SMTP или сбое отправки административное письмо остаётся в очереди с повторными попытками. Если проверка CE не удалась, отображаются последняя известная сумма и ошибка; неизвестный баланс не подменяется нулём. После двух интервалов без успешной проверки данные помечаются устаревшими. При отключённом мониторинге отправка этих писем прекращается.

Метрики `proxiapp_provider_account_balance_usd`, `proxiapp_provider_account_low_balance_threshold_usd` и `proxiapp_provider_account_balance_check_healthy` включены в Grafana и правила Prometheus. Доставка письма идёт через worker и SMTP. В Prometheus правила доступны для просмотра; для его собственной рассылки нужен настроенный Alertmanager.

Для других поставщиков маршрутизация и перепривязка ключей общие, но получение баланса аккаунта требует отдельного адаптера их management API. Совместимость с OpenAI inference API сама по себе такого метода не гарантирует.

## 14. Частые проблемы

`NO_UPSTREAM_CAPACITY` / товар «нет мест» — нет свободных мест на проверенных credentials. Сначала посмотрите причину последнего отказа в админке; если ключи пригодны, учитываются выданные ключи, неподтверждённые резервы и оплаченные заказы в ожидании. Добавьте рабочий credential или дождитесь освобождения мест.

`MODEL_NOT_PRICED` — модель не добавлена или отключена в тарифах выбранного пула. Это защитный отказ: запрос не отправляется, пока невозможно посчитать себестоимость.

`UPSTREAM_BUSY` — достигнут `maxConcurrency` конкретного upstream credential. Увеличивайте его только в пределах реальных ограничений провайдера.

Credential стал `DEGRADED` — откройте логи worker и проверьте баланс, API key, Base URL и `/v1/models`. `EXHAUSTED` не активируется worker автоматически: увеличьте spend limit или добавьте новый ключ.

`CREDITS_EXHAUSTED` / HTTP 402 означает, что баланс исчерпан. Пополните бессрочный ключ в кабинете, чтобы продолжить работу с ним.

Grafana через `/grafana/` не открывается — проверьте `GF_SERVER_ROOT_URL`, `PUBLIC_APP_URL`, контейнер `grafana` и Nginx DNS.
