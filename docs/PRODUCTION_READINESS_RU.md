# Готовность ProxyKey к продажам через Codex Everywhere

Актуальный план на 22 ноября 2026 года — [первый релиз только с USDT TON](CRYPTO_LAUNCH_RU.md). До получения реквизитов и живой сверки локальный стенд остаётся тестовым. Релиз зависит прежде всего от рабочего PayGo-ключа CE, сверки фактической себестоимости и проверки платежных провайдеров. `SALES_ENABLED` по умолчанию выключен в `production`; выключение останавливает новые заказы, а оплаченные заказы и действующие ключи продолжат обслуживаться.

## Что показал кабинет CE

Группы CE требуют отдельных ключей. В ProxyKey у Plus PayGo, Pro PayGo, Claude Max, Claude Kiro, Grok Heavy, DeepSeek и Images отдельные каналы, объединённые в один пользовательский каталог. Gemini описан как бета в документации, но в списке групп проверенного аккаунта его выдачи не было. Отдельная ставка для `codex-auto-review` не опубликована. [Модели и группы CE](https://docs.codex-everywhere.com/models/).

У существующего ключа Free Trial интерфейс показывал активный ключ, но `GET /v1/models` и один минимальный `POST /v1/responses` на модели из **Use Key** вернули HTTP `403` с причиной `no active subscription found for this group`. Это живой результат только для открытого ключа. Каталог и генерация платной группы, кеш, вызовы инструментов и длинный контекст на CE остаются непроверенными. Ключ не сохранялся, группу и баланс не меняли.

Кабинет CE разделяет баланс, ключи, расход и состояние каналов. На экране ключа показываются группа, квота и конфиги по клиентам, а в Usage — разбивка по моделям и экспорт CSV. В Channel Status различаются пинг endpoint и время ответа модели. Для ProxyKey это ориентиры: покупателю полезны модели и настройки его ключа, оператору — расход и история работоспособности каждой группы.

Флаг `CE_AUTO_PROVISION_KEYS` включает выпуск ключей через HTTP API кабинета CE из пополненного аккаунта. Параметры сверены с опубликованным веб-клиентом кабинета. Выпуск, обновление сессии, восстановление после сбоя и проверка каталога проверены на имитаторе. Для коммерческого запуска нужен один успешный выпуск в настроенной PayGo-группе CE. [Настройка](USAGE_RU.md#автоматический-выпуск-ключей-ce).

Мониторинг общего баланса CE использует тот же `/api/v1/auth/me` и общую блокировку обновления сессии. Порог, интервал и повторы задаются в `.env`; письма отправляются на `ADMIN_ALERT_EMAIL`. Проверки выполняются и при достаточном запасе ключей. Получение суммы, сбой account API, дедупликация, повтор после восстановления баланса и ошибки доставки проверяются локальным HTTP-имитатором и PostgreSQL. Реальные получение баланса и доставка SMTP требуют настроенных `.env.ce` и SMTP. Ротация после исчерпания и при недостаточном остатке проверяется без расходования реальных средств. Первый запрос, на котором сам поставщик сообщил об отказе ключа, может вернуть ошибку; автоматического повторения уже отправленного inference-запроса нет.

## Исправленные риски и границы проверки

| Риск | Что изменилось | Чем подтверждено |
| --- | --- | --- |
| Продажа места на непроверенном ключе, ошибка каталога или повторное добавление ключа | Пригодный для продажи ключ должен иметь непустой проверенный каталог, хотя бы один активный тариф, действительный результат проверки и свободное место. Дубликаты одного секрета не создают места. | Имитация CE `403` и HTML `200`; каталог из нескольких моделей; проверка дубликата и третьей продажи при лимите `2`. |
| Клиент видел модели, которые не мог вызвать | `/v1/models` возвращает модели с подтверждённым тарифом и местом в подходящем канале. Модели без тарифа видны только в каталоге витрины, без доступа к вызовам. | Регрессионный тест на неизвестную ставку и заполненный канал. |
| Баланс отличался от суммы оплаты | Сумма оплаты полностью начисляется на ключ. Один баланс обслуживает разные протоколы; себестоимость записывается отдельно от розничного списания. | Проверки миграции старого ключа и расчёта Claude и Gemini с одним ключом на 20 USDT. |
| Нетарифицированный запрос через вложенный маршрут и доступ к состоянию общего аккаунта | Разрешены конкретные маршруты и методы. `responses/compact` проверяет модель и учитывает usage, если провайдер реализует маршрут. Для текста отключено хранение ответа; ID сохранённых ресурсов и фоновые запросы отклоняются, cache/session ID разделены по покупательским ключам. | Локальный HTTP-провайдер: обход маршрута, stateless compaction, изоляция идентификаторов, SSE, image billing. [Контракт compaction](https://developers.openai.com/api/docs/guides/compaction). |
| Два дорогих запроса одновременно использовали один остаток | Вместе с местом для запроса резервируется оценка затрат по ключу и счёту провайдера. Итог считается по usage. Поток без подтверждённого расхода помечается для сверки; резерв держится недолго, чтобы сразу не повторить расход. | Два параллельных запроса при малом остатке; оборванный HTTP-поток; проверка ledger и метрики. |
| Платёж подтверждён, но заказ потерян после повтора, задержки или нехватки места | Подписанный платёж сверяется по ID, валюте и сумме; для крипты также по фактически отправленной сумме и монете. Запись события и статус `PAID` атомарны. Worker повторяет выдачу; срок, лимит и пул берутся из сохранённых условий заказа. | Подписанные локальные Stripe/NOWPayments события, повтор после `503`, поздний платёж, неверная сумма и монета, выдача ровно одного ключа после возврата места. [Stripe](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page), [NOWPayments](https://nowpayments.io/blog/how-nowpayments-protects-crypto-payments-and-merchant-funds). |
| Здоровый процесс скрывал отсутствие канала | `/health/ready` проверяет приложение и PostgreSQL, `/health/serving` показывает наличие проверенного канала. Метрики различают время до первого байта, длительность потока, доступные для продажи места и оплату без выдачи. | Локальный стенд и проверки PostgreSQL. Проверка каталога подтверждает доступ, но не заменяет модельный синтетический запрос. |

Локальные проверки используют PostgreSQL и управляемый HTTP-имитатор провайдера, а уведомления об оплате подписываются тестовыми секретами. Каталог Orbit не нашёл контракт CE; публичные материалы и открытый кабинет дали исходные данные для имитации. Postman CLI не привязан к аккаунту или workspace; доставка с реального ЮKassa/NOWPayments на публичный endpoint пока не проверялась.

## Что закрыть перед включением продаж

1. **CE и учёт.** Проверить выпуск отдельного Plus PayGo-ключа с лимитом расхода. Убедиться, что `/v1/models` доступен, сделать через ProxyKey обычный и потоковый Responses-запрос, инструмент и длинную сессию, включая compaction. Сверить отдельные строки CE Usage с ledger: input, cached, output, длинный контекст и тариф выбранной группы. Сравнить распределение с двумя реальными сессиями на одном credential. При PayGo лимит `2` задаёт количество мест. Пополнение работает по [инструкции CE](https://docs.codex-everywhere.com/account/), коммерческие условия обсуждаются с [командой CE](https://docs.codex-everywhere.com/business/).
2. **Деньги.** Прогнать ЮKassa test/live и NOWPayments sandbox с реальными уведомлениями на staging: успешный платёж, подтверждение после срока, недоплата, повтор и провайдер без места. Определить маршрут возврата/chargeback и сверку платежей с кабинетом. Для ЮKassa подтверждённый `payment.succeeded` восстанавливает потерянный ID созданного платежа после авторизованного GET и проверки условий заказа. Потерянный криптосчёт требует ручной сверки; автоматического возврата и dispute reconciliation сейчас нет. Продажная цена × `PRICE_MARKUP` не равна прибыли: учитывать комиссию, возвраты, налоги и расхождения тарификации.
3. **Лимит расходов и сбои.** Резерв по локальной оценке защищает от гонки, но не является строгой верхней границей счёта CE, особенно при неизвестном usage, длинном контексте, при обрыве или при повторном запросе клиента. Настроить реальный коммерческий лимит у CE по ключу/аккаунту; добавить сверку списаний, идемпотентность клиентского checkout и правила обработки неполных потоков. Провести нагрузочный прогон длинных SSE через Nginx и проверить отказ одного канала при работающем резервном.
4. **Публичный контур.** Настроить HTTPS и доверенные адреса ingress, ограничить Grafana и админку, заменить секреты и настроить доставку Prometheus-алертов. Сделать резервную копию PostgreSQL и восстановить её на другой базе; внести правила обновления образов и срок хранения данных. Добавить проверку почты при регистрации, восстановление доступа и второй фактор для админов. Колима — локальный стенд; продовый deployment и GitHub Actions на удалённом runner должны пройти отдельно.

## Улучшения кабинета после пилота

В кабинете доступны конфигурации подключения и история списаний. Доступ к каждому семейству зависит от мест в соответствующем канале. Для гарантированного набора семейств в конкретном пакете потребуется заранее резервировать места в каждом из них и отражать это в условиях пакета.

### Переход на RUB / USDT

Добавлена миграция 010 с сохранением старых остатков, валют исходных платежей и отдельной суммой зачисления USDT. ЮKassa проверяется запросом GET к API, а USDT TON — подписью IPN и точной суммой. Курс RUB фиксируется в заказе. Реальные реквизиты ЮKassa и NOWPayments не настроены; реальные платежи и доставка внешних webhook на публичный адрес требуют проверки на staging. Автоматические возвраты и chargeback reconciliation не добавлены.

### Проверка RUB / USDT и списка ключей CE

Локально прошли 48 тестов на Node 24 и PostgreSQL 16: сохранение старого баланса при миграции, рублёвый счёт с фиксированным USDT-зачислением, повтор / задержка webhook, недоплата и неверная монета, GET-проверка ЮKassa, расход после покупки за RUB, пополнение в USDT TON, постраничная синхронизация CE, отказ на частичной странице, общий остаток поставщика у двух клиентов и запрет административных данных для обычного пользователя. Сборка и TypeScript также проходят. Проверка внешних платежей и реального списка аккаунта CE остаётся отдельным шагом после настройки реквизитов.

### Аудит приложения 18 ноября 2026 года

Итоговый прогон: 55 тестов в 13 API-файлах прошли, включая миграции, покупки/пополнения, сессии и изоляцию владельцев, CE и конкурентные запросы. TypeScript, сборка React и все четыре локальных Compose-образа собираются. `/health/ready` на тестовой базе возвращает 200 и 12 миграций. Отдельных автоматических UI-тестов пока нет; интерфейс проверен через браузер в сценариях ниже.

Исправлены потеря подтверждённого платежа ЮKassa после потерянного ответа создания счёта, гонка удаления последнего активного администратора, доступ к сохранённым prompt templates общего аккаунта и запросы с нетарифицированными tier/audio опциями. Прерванный Anthropic-поток с частичным usage теперь сохраняет известные списания и временный резерв с отметкой `USAGE_UNCONFIRMED`.

Миграция 012 добавляет повторы пользовательских email. Отсутствие SMTP больше не считается успешной отправкой; ошибки повторяются с задержкой, конкурентные worker блокируют текущую доставку. Worker прерывает минутное ожидание по SIGTERM; проверка остановки завершилась с кодом 0. Ошибка чтения баланса провайдера сразу помечает последнюю сумму устаревшей.

В интерфейсе исправлены скрытые ошибки сохранения профиля и управления пользователями, устаревший баланс после обновления расхода и ложные нулевые показатели при ошибке загрузки. Браузерная проверка на одноразовой базе подтвердила валидацию профиля, видимый отказ блокировки самого себя, сообщение об искусственном HTTP 503 статистики и восстановление после кнопки «Повторить».

Проверки выполняются на отдельной PostgreSQL 16 и Node 24 с локальными HTTP-имитаторами. Реальные платежи, отправка email и платные inference-запросы не выполнялись. Основная база и `.env.ce` не изменялись. Новую миграцию применит следующий `docker-compose up -d --build`. Рабочие API/worker-образы содержат только production-зависимости API; Vite, Vitest, picomatch и другие инструменты разработки в них отсутствуют.

### Зависимости сборки: история проверки picomatch

На 18 ноября 2026 года полный `npm audit --audit-level=high` завершается с ошибкой из-за ReDoS [GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf) в `picomatch`, который используется через Vite/Vitest, tinyglobby и fdir. Advisory указывает уязвимые версии до `4.0.7` включительно и отсутствие исправленной версии. Проверка официального npm registry командой `npm view picomatch dist-tags versions --json` подтверждает, что последняя опубликованная версия — `4.0.7`, уже установленная в проекте. Предложенное `npm audit fix --force` понижение Vitest не устраняет подтверждённую причину и не применялось; проверка audit в CI сохранена и остаётся красной до исправления зависимости.

`npm ls picomatch --omit=dev` не показывает эту библиотеку среди зависимостей рабочего приложения; `npm audit --omit=dev --audit-level=high` на ту же дату завершился успешно с нулём известных уязвимостей. Уязвимость инструментария сборки остаётся открытой. После публикации исправления нужно обновить lockfile, повторить полный audit, тесты и сборку.

Обновление 22 ноября 2026: advisory GHSA-fc5q-39xc-vjpf отозван как не являющийся проблемой безопасности. Текущий полный `npm audit` возвращает 0 известных уязвимостей. CI audit не отключался; прежний блокер снят по обновлённым данным реестра, без принудительного downgrade.

### Проверка 22 ноября: первый релиз с криптооплатой

74 теста в 15 API-файлах прошли на отдельной PostgreSQL 16 / Node 24. Проверены повторный запуск миграций, TypeScript, сборка всех четырёх Compose-образов, Nginx `-t` и 10 правил Prometheus через `promtool`. Полный npm audit сообщает 0 известных уязвимостей. Удалённые GitHub Actions не запускались; проверки выполнены локально. Сканирование ОС внутри всех сторонних Docker-образов этим npm audit не покрывается.

Добавлены `PAYMENT_CURRENCIES=USDT` и запрет выключенной валюты на сервере. В витрине, покупке, калькуляторе и пользовательской документации убраны обещания рублёвой оплаты; сохранена история старых счетов. Браузерная проверка синтетического стенда подтвердила русский/английский интерфейс, светлую тему и создание счёта ровно на 20 USDT в сети TON. Реальные реквизиты оплаты не использовались.

Исправлен доступ старых mock/тестовых ЮKassa-ключей к платным каналам после переключения в production. Такие ключи и их пополнения теперь отклоняются до обращения к модели. NOWPayments получает точную сумму USDT; сетевые сбои дают контролируемый 503, неверный ID/адрес и уже истёкший счёт отклоняются. Проверка startup запрещает mock, sandbox NOWPayments и несовместимые валюту/способ при включении продаж.

Команда `production:check` проверена как с успешной синтетической конфигурацией, так и на текущем стенде, где она завершилась с ожидаемым кодом 1: development/mock, отсутствуют реквизиты NOWPayments и SMTP, нет публичного HTTPS-адреса и активного платного провайдера, в БД остался пароль администратора из разработки. Реквизиты, пароль и внешнее развёртывание не менялись. Новые боевые продажи не включены.

Контрольный тест подтверждает раздельно: 1000 входных, 200 кешированных, 500 выходных токенов; себестоимость 0.00182000 USD и списание 0.00364000 USDT. Токены учитываются 1:1, денежные ставки ×2. Текущая рабочая БД содержит только mock-заказы: фактическая коммерческая прибыль пока не подтверждена продажами. Формула и условия её применимости описаны в [плане запуска](CRYPTO_LAUNCH_RU.md).
